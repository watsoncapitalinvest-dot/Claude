BUILD -> MAPS, 13 Nov 2026 15:35: THE 255-PART CAP IS GONE (John 15:16: "can we make it more")

WHAT CHANGED
- A map can now use up to 65,535 part ids across its terrain sets, instead of 255.
- You no longer need to drop props (water towers, houses, tow trucks) to stay under the budget.

HOW TO WRITE ONE
- Save the map as NAME.MAP2 instead of NAME.MAP, in the same MAPS folder.
- Header: the same 3 bytes as a .MAP (rows, columns, levels).
- Tile order: the same as a .MAP.
- Each tile: 4 parts (floor, west wall, north wall, object), each part 2 bytes, little-endian (low byte first). 8 bytes a tile.
- Part ids count across the terrain's set list exactly as before (BLANKS first), just past 255.
- If a NAME.MAP2 and a NAME.MAP both exist, the game reads the .MAP2.

BUDGET (John 15:32: the game must still play)
- Keep a map under 1,000 parts in all. Every part's full-colour frame is held in memory (about 80 KB each), and John's game is a 32-bit build, so a few thousand parts in one battle can run it out of memory.
- Every part id the map uses must exist in its terrain sets. Check that with testblock before sending, as now; a bad id stops the battle from loading.

WHAT STAYS THE SAME
- Each terrain SET still holds at most 255 parts (its die/alt references are one byte). For more parts, split a big set into several sets of up to 255 each and list them all in the terrain.
- Route nodes: 251 per map file.
- Everything else: RMP, MCD, PCK/TAB, the _4X sheets, the ruleset.

WHEN IT WORKS IN THE GAME
- Game builds from commit 0193a43 on. John's PC does not have that build yet; it comes with the next delivery.
- Until then send .MAP files for anything John should play now. You can send both a .MAP and a .MAP2 of the same map.
